# Interface Assembly
## A Whitepaper for Humans

---

### I. You do not need to understand every technical detail to build software

That is the first thing to know.

A better way is to treat software like a machine made of big boxes or blocks or legos. Each block has a name, a job, and a clean connection to the other blocks. You do not need to learn how to manufacture plastic to build a city out of Legos. You need the right blocks, clear labels and an agent that knows how to fit them together without breaking the structure.

The human decides what the machine should do. The agent studies the folder, explains the blocks and builds the inside while keeping the public rules stable.

The goal is not to turn you into a compiler engineer. The goal is to help you think in clear pieces and let the agents handle the wiring. You are using a computer to read this without ever knowing how silicon wafers or chipsets are made. The same logic applies here. You do not need to understand every hidden layer of the software to build something useful.

You do not start with random code. You start with:
- the world
- the big boxes built by others
- the interfaces between them

One block might own profiles. Another might own posts or run a social network. Another might run a game. Another might own memory. Another might own the brain that explains what is happening. Another might own a market, or sub-agents that test whether ideas are strong or weak. Another might run a SaaS or an ecommerce store through its own containerized sub-agents.

The agent keeps the boundaries clear. That makes the product and software you are creating easier to understand, easier to change, more secure, and harder to break.

---

### II. The method is called Clause Coding or Block Coding

Interface Assembly rests on a practical method. A clause is a small rule or law, akin to the laws of a constitution, a charter or a contract. It says what something is, what it owns, what it may do, what it may not do and how it connects to other parts/boxes of the world or to other worlds (networks)

These clauses become boxes. With enough boxes stacked, you can create skyscrapers. In that sense, software stops feeling like a pile of mystery and starts feeling like a machine with parts you can name.

Vibe coding is often how a project begins. A person has a feeling, a direction, a burst of energy, and asks a model to make something fast. That is useful. It helps a project start moving. But once the thing begins to matter, it needs stronger structure and clearly defined components.

Interface Assembly turns vibes into clauses, clauses into boxes and boxes into a system that can grow without collapsing.

The method in six steps:

1. Name the world.
2. Name the big boxes.
3. Write the clauses that define them.
4. Keep the interfaces clean.
5. Let memory survive.
6. Let the agent read the structure, explain the structure and build inside the structure.

Humans stay human. Agents handle the machinery.

If you can still navigate the world after it grows, the method is working.

---

### III. Memory matters

The system keeps memory. If you keep choosing the same layout, naming style or build pattern, the agent remembers it. If an older rule is replaced, the system marks it as old instead of pretending it never existed. This helps the agent learn how you like to build.

This system should feel like a Gistbook or GistHub for your thinking and instructions to your agents. Your prompts, interfaces, notes, changes and decisions should be visible. Your agent should show you what changed, which block it touched, and what tests prove it works.

That way you and the agent can grow together instead of starting over every time the project changes shape.

---

### IV. We build on the shoulders of giants who wrote open source code and run open access infrastructure

Cypherpunks write code. There are countless to name.

Networks are not just computer systems, blockchains, or tokens. They are people, places and communities. These communities have provided us all the blocks that may one day build skyscrapers.

Everyone is needed. Everyone is necessary. Everyone holds a concept of an idea that can generate a unique interface or spawn a unicorn.

---

### V. You can build anything without seeking permission

**1. The first and easiest way** is to copy and paste this article into your chatbot with the github link and ask it what to do.

**2. The second and optimal way** is VS Code. Open the folder. Install the coding-agent extension. Tell the agent to read the handbook and docs. Then let it study the project, explain the boxes, and build step by step.

**3. The third way** is GitHub plus Codex or Claude. Fork the repo or put the files into a GitHub repository. Connect GitHub to Codex. Then let Codex work with the repository directly and open pull requests with its changes. Codex can connect to GitHub repositories, work with code in them and create pull requests from its work. That means some people can use this without even opening VS Code if they prefer a GitHub workflow.


---

### VI. Weak devices are still enough

If your laptop is weak, that is still fine.

You can do a lot from a phone, tablet or light computer by using remote inference and repo-based workflows. One API can reach many models. That can help move heavy model work off a weak device and into hosted services.

The important point is that you do not require a perfect high-end machine to write complex software. You just need to start with the right structure and let the agents handle the wiring and heavy lifting.

---

### VII. How to start

1. Download or clone this repository.
2. Open the folder in VS Code.
3. Read `README.md` first.
4. Read `world/WORLD.md` to see the starter world.
5. Read `hub/README.md` to understand the public-facing roles and skill cards.
6. Read `constitution.md` if you want the operating rules in one place.
7. Ask your coding agent to read the repo before making any changes.
8. Start by naming your world, then your boxes, then your interfaces.

What to do first inside the starter:

1. Replace the example world language with your own project language where needed.
2. Write your first real proposal in `world/proposals/`.
3. Define or revise boxes through clauses in `world/clauses/`.
4. Keep shared contracts in `world/interfaces/`.
5. Keep external tool or repo edges in `world/adapters/`.
6. Record accepted structure clearly so the next human or agent can still read the world.
